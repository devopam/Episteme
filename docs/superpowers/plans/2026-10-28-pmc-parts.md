# PMC in Bounded Parts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extract PMC (about 935k articles) as fixed id buckets written in bounded parts, with resume, retire, a streaming graph phase, a sample slice and gate rules.

**Architecture:** Discovery groups the metadata files into fixed buckets of PMC ids and writes one small manifest per bucket; the existing process pool runs one bucket per task from its manifest; each bucket streams its rows into parts capped by `part_rows`/`part_bytes`, as pubchem does. The pubchem retire path becomes a shared module used by both sources.

**Tech Stack:** Python 3.13, pyarrow, psycopg 3, PostgreSQL 19beta3, pytest.

**Spec:** `docs/superpowers/specs/2026-10-28-pmc-parts-design.md` (approved 2026-10-28).

## Global Constraints

- `src/episteme/config.py` is the only module that reads `os.environ`.
- Endpoint URLs live only in `scripts/data/_lib/sources.env`; `grep -REn 'ftp\.|s3://|https?://' scripts/data/ | grep -v _lib/sources.env | grep -vE ':[0-9]+:\s*#'` prints nothing.
- Every marker key and stored `source_file` is a part or bucket name built by this plan's functions, never a bare basename; the identity rules have a collision test.
- `BUCKET_IDS = 50_000`; bucket key `pmc_b{bucket:04d}`; part name `pmc_b{bucket:04d}__part{n:05d}`.
- Audit event for a written part: `extract_commit` (an existing `EVENT_TYPES` member).
- Rows stream into `write_rows`; no function holds a whole bucket's rows in memory.
- Run `ruff format` and `ruff check` on changed Python before each commit; `git add` explicit paths only; never `--no-verify`.
- Non-pg tests: `uv run pytest -m "not pg" -q`. Pg tests: `set -a; . ../Episteme/.env; set +a; EPISTEME_DB_MODE=restricted PGDATABASE=episteme_test uv run pytest -m pg -q <files>`; after any pg run, re-apply the `episteme_test` migrations with the controller's script (the controller does this, not the implementer).
- No real-data run on D: by an implementer. Tests use `tmp_path` fixtures only.
- Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_01XrLEbkf9BAxrqFTBfcU48z`.

## Review Focus

1. The same article id and version in two download subfolders → one row; the other is counted as `duplicate_files`; no crash (Task 2 test `test_same_version_in_two_folders_keeps_one`).
2. A metadata file whose name is not `PMC<digits>.<digits>.json` → skipped, counted as `unrecognised_files` in the run summary, with a warning; the run goes on (Task 2 test `test_unrecognised_names_are_counted_not_fatal`).
3. A rebuilt bucket that now needs fewer parts than before → the extra old parts are deleted, and those that were loaded go to the retire pending list (Task 3 test `test_rebuild_with_fewer_parts_retires_the_extra_loaded_parts`).
4. A metadata file with no matching XML → still one row (metadata-only), as today (Task 3 test `test_metadata_without_xml_still_writes_a_row`).
5. A stop after some parts of a bucket → the next run writes the bucket again from part 1 and leaves no part from the stopped run (Task 3 test `test_partial_bucket_is_written_again_from_part_one`).

### Task 3: Bucket extraction in parts

**Files:**
- Modify: `src/episteme/data/pmc/extract_pmc.py` (new `process_bucket`; `extract_pmc` drives buckets; the per-file `process_one` is removed; `row_from_meta_and_xml` and `find_xml_for_meta` stay unchanged)

**Interfaces:**
- Consumes: Task 2 (`group_by_bucket`, `write_manifest`, `read_manifest`, `part_name`, `bucket_fingerprint`), Task 1 (`parts_retire.add_retire_pending`), `staging_writer.write_rows`, `parallel.run_per_file`, `checkpoint_markers.*`, the profile's `part_rows` / `part_bytes` (through a `_part_caps()` seam, as in pubchem).
- Produces:
  - `pmc_row_bytes(row: dict) -> int` — UTF-8 bytes of every string value and every string element of a list value, plus `PART_ROW_OVERHEAD_BYTES` (import the pubchem constant).
  - `process_bucket(manifest_path: Path, *, raw_dir: Path, processed_dir: Path, force: bool) -> dict` — returns `{"source_file": key, "ok", "skipped", "parts", "n_rows", "failed_articles", ...}`.
  - `extract_pmc(...)` keeps its signature; `max_files` now limits the number of buckets; `skip_units` take bucket keys; the summary adds `buckets`, `unrecognised_files`, `superseded_versions`, `duplicate_files`, `failed_articles`.

Behaviour (spec 4.2, 4.3, 5):
- Skip when the bucket marker exists and its `inputs` equal the manifest fingerprint (unless `force`).
- Otherwise delete every existing part of the bucket first (markers, then shards, then load markers), adding the names of loaded parts to the retire pending list before any delete, as `serialize_pubchem._delete_parts_above(key, 0)` does; then write from part 1.
- Rows stream from a generator into `write_rows`; a part ends before a row that would take it past `part_bytes`, or at `part_rows`; a single row larger than `part_bytes` is its own part.
- Each part writes its success marker (`n_rows`, `first_pmcid`, `last_pmcid`, `extract_status_counts`, `part_rows`, `part_bytes`, `est_bytes`, `write`) and one `extract_commit` audit row (best effort, as today).
- An article whose parse raises is skipped in the part, recorded in the bucket stats `failed_articles` (`[{"file": input_key, "error": str}]`, at most 100 listed plus a count) and in `mark_failed(processed_dir, "pmc", <article input_key>)`.
- The bucket marker lists `parts`, `parts_list`, `n_rows`, `superseded_versions`, `duplicate_files`, `failed_articles` count and `inputs` (the fingerprint).
