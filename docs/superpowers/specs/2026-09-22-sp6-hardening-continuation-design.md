# SP6 — Hardening Continuation: design

**Date:** 2026-09-22
**Status:** Approved (user: "yes, please proceed uninterrupted")
**Depends on:** SP1–SP5 merged to `main` (SP5 = PR #6, merge commit `6a9ce4d`).

## 1. Goal

Close the deferred bucket left after SP4.1 and SP5: dependency cleanup, audit-trail hardening, two pipeline correctness bugs (one small, one large — the SP2-extractor identity migration), and the cdisc_bc licence posture. No new subsystems; this hardens what SP1–SP5 already built.

## 2. Findings that shaped scope (verified in code/web before writing this spec)

- **Dependency cleanup is far lower-risk than assumed.** All 4 cryptography Dependabot alerts and the diskcache alert trace to exactly one dependency: `pyeuropepmc` (declared in `pyproject.toml`'s `data` extra). The only import site in the whole tree is `src/episteme/data/_legacy_download.py`, whose own module docstring reads `"""PARKED — pre-restructure multi-source downloader. Not imported anywhere. ... Kept for reference + git history until each function has a real home."""`, and which already wraps the import in `try/except ImportError`. `nltk` (the 6th alert) has zero references anywhere in `src/`, `scripts/`, or `tests/` beyond its own `pyproject.toml` line. Removing both closes 6/7 alerts with no behavioural change. `accelerate` (7th) is genuinely used — HuggingFace `Trainer` in `src/episteme/model/train_continual_pretraining.py` picks it up implicitly — and has no patched version on PyPI as of this writing; it stays open, reported not fixed.
- **`download_pmc.py` hardcodes its output path.** `main()`'s `--output_dir` default is the literal `Path("./01_raw/pmc/oa_comm")`. `extract_pmc.py`'s equivalent default is `settings.raw_root / "pmc" / "oa_comm"` — the correct pattern already exists next door. `scripts/data/pmc/download_pmc.sh` never passes `--output_dir`, and `run_pipeline.sh` never passes it either, so PMC downloads silently ignore `EPISTEME_DATA_ROOT`/`EPISTEME_RAW_ROOT` today; the bug is latent because default configs happen to agree.
- **The tests/data env leak is unidentified**, not un-diagnosed-in-principle: the SP4.1 `fresh_config` leak (test_config.py) was root-caused and fixed (commit `281e42f`/`0abf911`); the SP5 close-out batch (`29a16e5`) hit a *different* failure — the re-keyed no-leak canary tripped in a full-suite run but not when `tests/data` + `test_config.py` ran alone. That means the actual leaking test lives outside both directories, or the leak is order-sensitive across the top-level `tests/` files. This needs bisection, not another guess.
- **Audit-trail gaps are exactly what `docs/11-gxp-data-integrity.md` §5/§8 already state** (SP5 verified these against code): no partition auto-creation (`schema.sql` comment: `"episteme.create_audit_partition() / a rotation script is not yet [implemented]"`), only `_audit_202609`/`_audit_202610`/`_audit_default` exist; `REVOKE UPDATE, DELETE` is per-partition and does not propagate to a newly created one (`ALTER DEFAULT PRIVILEGES` only *grants*); no mirror rotation/`chattr +a`; `manual_correction`/`schema_migration`/`integrity_check` have no live call site and no enforced `reason`; extract/serialize `_best_effort_audit` swallows every exception silently past the mirror-failure path.
- **cdisc_bc licence spike, concluded (web research, 2026-09-22):** the COSMoS README states code/scripts are MIT and "documentation and minutes" are CC-BY-4.0, and is silent on the `export/` data files. CDISC's site-wide Terms and Conditions (`cdisc.org/terms-and-conditions`) grant a "nonexclusive, worldwide, perpetual, compensation-free" licence to CDISC standards "solely within Your Organization," explicitly excluding "the right to (i) translate or create derivative works" and excluding "internally or externally copy, distribute, or post to a Web page" — but that page's stated scope is "CDISC standards in document format," not clearly this GitHub repo's exports. The ambiguity cannot be resolved further without CDISC confirming directly, which is outside this agent's reach. **Decision (user, 2026-09-22): lock in download-only, no serializer, no corpus inclusion, until CDISC confirms.**

## 3. Scope — four phases

### Phase A — Dependency cleanup
Remove `pyeuropepmc` and `nltk` from `pyproject.toml`. Regenerate `uv.lock`. Confirm via `grep` that no live import references either, then run the full non-pg suite. Report `accelerate` as still open (no fix available) in the drift log.

### Phase B — Audit-trail hardening
1. `scripts/data/db/ensure_audit_partitions.sh`: idempotent, creates `episteme._audit_YYYYMM` for a rolling window of upcoming months (default 6) if not already present, and re-applies `REVOKE UPDATE, DELETE ... FROM episteme_app` on every partition it creates (existing ones are untouched — already revoked). Uses the same `PSQL=`/venv-discovery conventions as `scripts/data/db/migrate_database.sh`. Documented as a periodic operator step in `docs/10` (exact wiring — cron note vs. manual step — decided at plan time to match existing script conventions).
2. `audit_trail.record()`: raise if `event_type in {"manual_correction", "schema_migration"}` and `reason` is falsy (mirrors the existing CLI-level enforcement for `force_override`; zero live call sites today, so zero behavioural risk).
3. `scripts/data/rotate_audit_logs.sh`: gzip `_ops/_audit/audit-YYYYMMDD.jsonl` mirror files older than 30 days in place (`audit-YYYYMMDD.jsonl` → `audit-YYYYMMDD.jsonl.gz`); best-effort `chattr +a` on the *current* day's mirror file on Linux (`command -v chattr` guard; no-op elsewhere, including Windows). `verify_audit_trail.sh`'s existing `.jsonl`/`.jsonl.gz` glob already covers rotated files — confirm with a test, do not re-implement.
4. Extract/serialize `_best_effort_audit`'s inner bare `except: pass` (the one that runs after `mirror_only` itself has already failed) becomes `except Exception: log.warning(...)` — still swallows the failure (ingestion must not block on audit), now observable.
5. Update `docs/11` §5/§8 to describe the fix instead of the gap; keep everything else in that document unchanged.

### Phase C — Pipeline correctness
1. **`download_pmc.py`** (small, low-risk): default `--output_dir` to `settings.raw_root / "pmc" / "oa_comm"`, matching `extract_pmc.py`. Regression test: run with a custom `EPISTEME_DATA_ROOT` and confirm the resolved path follows it.
2. **tests/data env leak** (investigation task): bisect the full non-pg suite (binary-search by directory/file, `-p no:randomly` if applicable, comparing `os.environ` snapshots before/after each file) to find the actual leaking test; fix it with the same pattern as the SP4.1 fix (snapshot/restore, or a `monkeypatch` that the test isn't currently using); add a regression test that fails if the leak recurs.
3. **SP2-extractor identity migration** (largest, highest-risk): migrate all **seven** literature extractors — `pmc`, `pubmed`, `apollo`, `europepmc_manuscript`, `europepmc_preprint`, `guidelines`, `bookshelf` — to `discover_input_files`/`input_key` (the scheme SP4 migrated all 8 structured serializers to). **Correction to an earlier draft of this spec:** only `pubmed` and `apollo` literally call the shared legacy helper (`list_input_files`); the other five each hardcode `source_file = path.name` (or `meta_path.name`) independently, which is the same basename-identity hazard by a different route — verified by reading each module directly. `pmc` and `bookshelf` use `rglob` (recursive; real collision risk on nested layouts — `bookshelf`'s download layout nests nested tar members, and `pmc`'s discovery combines two separate `rglob` calls over `meta_dir` and `raw_dir`) and go first; `pubmed`/`apollo` (the two literal `list_input_files` callers) go next; `europepmc_manuscript`/`europepmc_preprint`/`guidelines` use a flat, non-recursive `raw_dir.glob(...)` where a basename collision is structurally impossible under the current download layout — lowest risk, migrated last for consistency and defense-in-depth. One task per extractor; each gets its own checkpoint/duplicate-detection test (the project's standing restartability thumb rule) before the next starts.

### Phase D — cdisc_bc licence posture
Docs/wrapper-only. Strengthen `scripts/data/cdisc_bc/download_cdisc_bc.sh`'s header, the `PROVENANCE.txt` template, and `docs/09` §3.3-equivalent / `docs/10` / `docs/12` wording to state explicitly: no serializer exists or is planned until CDISC confirms the `export/` data licence; this source must never be included in a training corpus in its current state. No functional code change — the wrapper is already download-only.

## 4. Out of scope
Any new source; any change to the DB-mode guard; SP5's docs (beyond the two named touch points in `docs/09`/`docs/10`/`docs/11`/`docs/12` above); `pmc`'s own dispatch chain unless Phase C.3 finds it shares the legacy path; contacting CDISC (outside this agent's reach).

## 5. Risks
- **Phase C.3 (SP2 migration) is the real risk in this SP** — it touches live literature ingestion. Mitigated by one extractor per task, a dedicated checkpoint-collision test per task (the exact hazard SP4 fixed for structured serializers), and per-task review before proceeding.
- **Phase B.1** (partition script) must not weaken the existing REVOKE — a test proves a newly created partition denies `UPDATE`/`DELETE` to `episteme_app`.
- **Phase A**: confirmed safe by absence of any live import; the full suite is the final check anyway.

## 6. Phasing (for the plan)
A (dependency cleanup) → B (audit hardening) → C.1 (pmc raw-root fix, small) → C.2 (env-leak bisection) → C.3 (SP2 migration: pmc, bookshelf, pubmed, apollo, europepmc_manuscript, europepmc_preprint, guidelines — in that order) → D (cdisc_bc wording) → full sweep, drift-log entry, whole-branch review.
